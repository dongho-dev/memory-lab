## 2026-11-07 · 프로젝트 시작 (원문: 로컬 `docs/sessions/2026-11-07.md`)

### 목표
- [소유자] 목적은 **더 좋은 메모리 시스템**을 만드는 것. 무관한 대화에 기억이 끼어드는 문제는 "작은 부분".
- [소유자] 잘 만들면 자기 에이전트들에 붙여 쓸 수 있다.
- [소유자] 가장 작은 것부터 시작한다.

### 배경
- [소유자] 노션에 L1–L5 계층 메모리를 만들어 운영했지만 지금은 잘 안 쓴다.
- [소유자] Claude 메모리를 켜면 관련 없는 대화에도 기억을 끼얹는 게 불쾌해서 꺼뒀다.
- [관찰] 그래서 노션 체계의 L1(항상 주입되는 포인터층)이 사실상 비어 있고, 새 대화는 "메모리 불러와"로 직접 시동을 걸어야만 노션을 읽는다.
- [제안] 안 쓰게 된 다른 원인 후보: 드리밍(오프라인 정리)이 없어 쓰기 부담이 전부 사람에게 감, 5단계 트리라 읽기 왕복이 많음. 소유자 확인은 아직 없음.

### 방법
- [합의] **가장 단순한 메모리(원문 검색)를 먼저 만들고, 이걸 이기는 층만 남긴다.** 정답률이 오르거나 토큰이 줄어야 남긴다. ("새로 만들자"로 기준선 키트 진행에 동의)
  - 근거 [관찰]: CL-Bench에서 단순 컨텍스트 학습이 메모리 전용 시스템을 이김. Anthropic 글에서도 위키 단독(48%)이 검색 단독(53%)보다 낮음.
- [합의] 평가는 LongMemEval 서브셋으로 시작한다. 정답률과 질문당 토큰을 본다.
- [소유자] 새 저장소 memory-lab에서 시작한다. `agent-memory` 저장소는 Grok 봇 메모리라 건드리지 않는다.
- [제안] 평가는 공개 벤치마크와 자체 제작을 섞는다. 도움·낡음은 LongMemEval, 침투는 OP-Bench/PersistBench류, 출처 혼동은 직접 만든다 (2026-11 조사 기준 전용 공개 벤치마크를 찾지 못함).
- [제안] 실사용 트랙을 따로 본다: "이번 주에 실제로 이걸 썼나". 노션 체계가 멈춘 이유가 정확도가 아니라 시동 비용이었기 때문.

### 설계 아이디어 (아직 제안 단계)
- **출처 태그**: 기억 항목마다 직접 발언 / 확정 / 검토안 / AI 해석을 구분한다.
  - 정정: 대화 중 Claude가 이걸 "제 제안"이라고 했지만, 이 네 구분은 원래 **[소유자] 노션 Agent Memory 루트의 운영 원칙**에 있던 것이다. memory-lab에 적용하는 것이 [제안].
- [제안] 드리밍 결과는 diff로 남기고 사람이 승인한다. 특히 'AI 해석 → 확정' 승격은 반드시 승인.
- [제안] 게이트: 턴마다 "기억 안 씀 / 조용히 반영 / 명시적 언급"을 정한다. 임베딩 유사도가 아니라 추론으로 (RPEval: 의미 유사도로는 무관한 기억을 거의 못 거른다).
- [제안] 메모리의 순가치 = 관련 질문에서의 이득 − 무관 질문에서의 손해. CL-Bench의 gain을 둘로 나눠 잰다.
- [제안] 전달은 MCP 서버(remember / recall / dream).
- [제안] 실전 테스트베드: claude-pipeline의 팁 풀. 리뷰어 PASS/FAIL과 CI가 객관적 피드백이라 효과를 숫자로 잴 수 있다.

### claude-pipeline에서 본 것 ([관찰] + [제안])
- 팁 풀(`tip-pool.json`): 실패 → 한 줄 요약 → 가중치 → 워커 프롬프트 끝에 랜덤 2개 주입. 노트층 + 주입층에 해당.
  - 실패만 기록, 가중치는 오르기만 함(망각 없음), 관련성 무관 랜덤 주입, 효과 측정 없음.
- 감사 학습(`audit-learning.json`): 오탐/채택 패턴을 count·last_seen과 함께 쌓고 90일 뒤 만료. 망각이 설계된 부분.
- blame 추적(계획): 여러 실행의 실패 원인을 모아 시스템을 고치는 단계. 드리밍에 해당.

### 기록 방식
- [제안] 대화는 원문(`docs/sessions/`) + 정리본(이 파일) + 목차(`CLAUDE.md`) 세 층으로 남긴다. 소유자 질문("전문을 넣어둘까? 정리해서? 손실날거 같긴 한데")에 대한 답. 별말 없으면 진행한다고 했고, 아직 확답은 없음.

### 열린 질문
- 노션 체계를 안 쓰게 된 이유 중 끼어들기 말고 다른 요인(낡음, 쓰기 부담)은 얼마나 컸나?
- 드리밍 주기와 망각 정책은 무엇을 기준으로 정하나 (접근 빈도? 정보 성격?)
- 자체 평가셋의 출처 혼동 문항은 어떻게 만들까?

## 2026-11-08 · 실행 방식

- [소유자] 모델 호출은 API 요금이 아니라 **이미 결제한 Claude 구독**으로 돌린다. ("구독 요금을 내가 결제했는데")
  - [관찰] Stage 0 하네스는 Anthropic API(종량제)로 짜여 있었다. 소유자가 정한 게 아니라 Claude가 처음 만들 때 고른 것.
  - [합의] 로컬 Claude Code CLI(`claude -p`)를 백엔드로 붙이고 기본값으로 한다. API는 `--backend api`로 남긴다. ("붙이는데")
- [소유자] 가장 작고 가벼운 것부터 한다. 질문당 약 16.5만 토큰을 넣는 `full_context`(_s 전체 이력)로 시작하지 않는다.
  - [합의] 기준선 기본 실행은 no_memory · raw_search_k10 · oracle_full. `full_context`는 상한 참고용으로 `FULL=1`일 때만 돌린다.
- [소유자] 답변 모델은 Haiku / Sonnet / Opus로 나눠 각각 시험한다. ("haiku / sonnet / opus 로 분리해서 나중에 각각 시험해야겠네")
  - [관찰] 첫 기준선(EXPERIMENTS 001)은 Sonnet으로 돌렸다. Sonnet은 Claude가 API 요금 기준으로 고른 것이었고, 소유자 에이전트는 주로 Opus·Haiku를 쓴다.
  - [제안] 같은 메모리 층이라도 모델 세대에 따라 이득이 다를 수 있다(CL-Bench: 고정 규칙이 강한 모델에는 손해, 약한 모델에는 이득). 그래서 층마다 세 모델 결과를 나란히 본다.
- [소유자] 메모리도 실행 방식도 작은 것부터 기록하며 천천히 살을 붙인다. 계층(노션 L1~L5)을 한 번에 붙이는 건 나중에. ("방식도 기록해가면서 천천히 살을 붙여보자고")
  - [합의] 실행 방식: 켜 둔 `claude` 프로세스에 `/clear`를 보내 문항마다 새 대화로 쓴다(`claude-code-session`, 기본값). ("응, 붙여")
  - [제안] 기본 검색(raw_search_k10)에 붙일 순서: 검색 개수 → 자르는 단위(라운드/세션) → 날짜·출처 꼬리표 → 선호 질문 검색어 확장 → … → 계층.
- [소유자] 저장소는 MIT로 공개할 생각이다. 개인 대화 원문(`docs/sessions/`)은 지우고 gitignore에 넣는다. ("mit로 하는데, 근데 내 노션 원문을 지우고 해야 하지 않을까? 그 gitignore에 넣어두고")
